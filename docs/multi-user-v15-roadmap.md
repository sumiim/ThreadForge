# ThreadForge 多用户路线

## 当前结论

V1.5 先建立归属和授权边界；后续增量已经接入 GitHub OAuth，支持一个可信实例内的白名单多用户。当前仍是单实例、单 Worker、全局单活动任务，不是可直接暴露公网的完整多租户版本，也不得通过客户端提交的 `X-User-Id` 判断身份。

本阶段已经实现：

- 使用稳定 UUID 为 Session、Task、Approval 和 Run 查询链路建立归属关系。
- 服务层与 Repository 层执行对象级归属校验，越权访问按不存在处理。
- 启动时将没有 `owner_id` 的 V1 历史记录一次性归属给当前实例所有者。
- `THREADFORGE_INSTANCE_OWNER_ID` 只由服务器配置，浏览器请求头不能覆盖。
- 可选 GitHub OAuth 使用服务端白名单建立可信身份，认证 Cookie 只保存不透明会话令牌。
- 原实例所有者首次登录后继承历史数据；其他 GitHub 用户获得独立 `owner_id`，对象级查询继续隔离。

## 部署约束

- 实例所有者 UUID 默认在首次启动时生成并持久化到数据目录；也可通过 `THREADFORGE_INSTANCE_OWNER_ID` 显式提供，但必须与已有值一致。
- 当前 API 继续仅监听 loopback，通过 SSH 隧道联调，不得直接开放公网端口。
- 2 至 5 人可信内测可以使用 GitHub OAuth 白名单共享一个实例，但所有用户仍共享全局任务并发额度、工作区和模型密钥。
- 同一工作区仍不能安全地并行执行多个写任务。

## V2 实施顺序

1. PostgreSQL 与 Alembic：迁移 Session、Task、Approval、Run 元数据和可靠事件表。
2. 组织与角色：在现有 GitHub OAuth 身份之上建立组织、成员和角色；需要企业身份集成时再增加 OIDC。
3. 对象级授权：所有 REST、SSE、审批、取消和制品接口统一验证组织及所有者。
4. 持久化调度：任务租约、心跳、幂等键、每用户/工作区并发额度和异常恢复。
5. 执行隔离：每任务独立 Git worktree，随后升级为非 root 容器并限制资源和网络。
6. 可靠事件：PostgreSQL outbox、事件序号和 `Last-Event-ID` 恢复；Redis 仅按实际吞吐需求引入。

## V2 上线门槛

- 用户 A 无法读取、订阅、审批、取消或下载用户 B 的任何对象。
- 同一工作区的并发写入不会相互覆盖。
- Worker 崩溃后任务租约能够收敛，事件能够断线续传。
- 数据库迁移、备份恢复、审计日志、限流和密钥轮换均经过演练。
- 域名、TLS、固定 CORS 来源和反向代理身份头清洗全部启用。
